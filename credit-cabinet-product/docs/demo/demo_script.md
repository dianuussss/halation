## Решение в одном абзаце
7,5 минут живого прототипа, слайдов — два. Демо идёт по E2E-01 (Анна) с врезками E2E-03 (эксперт) и E2E-06 (лента), потому что эти три сценария вместе закрывают все шесть критериев жюри. Самый рискованный по времени блок — автоматический конвейер: он идёт с паузой 3 с на переход, и пока статусы шагают, спикер рассказывает про скоринг. Если стенд падает — локальный Docker, затем запись; запись — только резерв.

## Подготовка стенда
- Вкладка 1 — клиент anna@demo.local · вкладка 2 — expert@demo.local · вкладка 3 — Swagger `/api/docs` · вкладка 4 — admin (журнал).
- Заранее (до выхода на сцену) подготовлена заявка marina (E2E-03 шаг 1), она уже в MANUAL_REVIEW — чтобы не тратить время на вторую анкету.
- `DEMO_STEP_DELAY_MS=3000`, `LLM_ENABLED=false` (если не уверены в железе), ускоренные TTL выключены, выполнен «Сбросить демо» → затем подготовлена заявка marina.
- Масштаб браузера 125%, режим «не беспокоить», уведомления ОС выключены.

## Ответы на вопросы жюри

1. **Почему эти 3 продукта и 2 роли?** Три продукта покрывают три разных потребности из кейса (быстрые деньги, крупная покупка, регулярные разрывы) и дают все пять исходов решения: один и тот же класс B даёт автоматическое одобрение у «Экспресса», эксперта у «Инвеста» и другой лимит у «Линии». Две банковские роли — минимум, чтобы показать разделение автоматики и экспертизы и проверяемость (аудит).
2. **Как устроен скоринг и почему не ML?** Стоп-факторы → балльная карта из 9 факторов → класс A–D → политика продукта. ML без реальных данных нечем обучить и валидировать, а балльная карта объяснима клиенту и аудиту. Правила — конфиг с версией, ML-модель встанет на место карты без изменения контрактов.
3. **Что будет, если БКИ не ответит?** Три ретрая с паузой, затем заявка уходит эксперту с флагом «неполные данные» — конвейер не падает и не отказывает автоматически. Это сценарий C6, его можно пройти самим.
4. **Как встроить в инфраструктуру банка?** Stateless API за балансировщиком, воркер конвейера масштабируется отдельно, моки заменяются адаптерами к реальным сервисам по тем же контрактам. Безопасность: JWT + RBAC, bcrypt, валидация файлов, клиент не видит внутренних данных. Аудит — append-only журнал всех переходов.
5. **Где ИИ и почему не больше?** Только объяснение решения простыми словами и сводка для эксперта, open-weights модель локально, за флагом и с шаблонным фолбэком. ИИ не принимает кредитных решений — это вопрос ответственности и объяснимости.
6. **Как проверяли потребности пользователей?** Честно: desk research по кейсу и публичным путям кредитования МСП, гипотезы помечены уровнем доказанности; подготовлен скрипт экспресс-интервью. Ключевые боли (статус, повторный ввод, непонятные причины) прямо следуют из кейса.
7. **Что дальше после хакатона?** Реальные интеграции (ФНС, БКИ) вместо моков, ML-скоринг с валидацией на исторических данных, КЭП-подписание, кредитный комитет и лимиты полномочий, несколько компаний и приглашение бухгалтера, CMS для ленты.

## Инструкция для самостоятельной проверки жюри (вставляется в README)
1. `git clone <repo> && cd <repo> && git checkout v1.0-hackathon`
2. `cp .env.example .env`
3. `docker compose up -d` (первый запуск ≈ 3–5 мин)
4. Открыть `http://localhost:3000`, войти `anna@demo.local / Demo2026!` → пройти E2E-01 по [test_scenarios](../testing/test_scenarios.md).
5. Войти `marina@demo.local`, подать заявку E2E-03 шаг 1 → `expert@demo.local` → одобрить.
6. Сравнить ленты anna и igor (E2E-06), предварительно подав заявку igor (E2E-02).
7. Открыть Swagger `http://localhost:8080/api/docs`.
