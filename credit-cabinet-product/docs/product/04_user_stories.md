# User stories с критериями приёмки (D4)
Статус: готов · Версия: 1.0 · Обновлено: 2026-10-24
Связано с: R-03…R-08, R-21 · [01_research](01_research.md) · [03_story_map](03_story_map.md) · экраны [screens](../ux/screens.md) · тесты [test_scenarios](../testing/test_scenarios.md)

## Решение в одном абзаце
26 Must-историй описывают ровно сквозной путь из [03_story_map](03_story_map.md); у каждой — связь с JTBD/болью, экраном и тестом, ≥ 2 AC в формате Given/When/Then, из них ≥ 1 негативный (помечен ⛔). Статусы в AC — только из [state_machine](../process/state_machine.md), числа — из [scoring_and_decision](../process/scoring_and_decision.md). Should/Could описаны короче — они не блокируют релиз.

Обозначения: **Пр.** — приоритет · **Связь** — JTBD/боль · **Экран** · **Тест** — сценарий проверки.

## Клиент

### US-C-01. Вход по тестовой учётке
Как представитель компании, я хочу войти в кабинет по логину и паролю, чтобы видеть свои заявки и компании.
Пр.: Must · Связь: P-C8 · Экран: S-01 · Тест: E2E-01 шаг 1, NEG-06
- Given `DEMO_MODE=true`, When открыта страница входа, Then под формой виден список тестовых учёток с ролями.
- Given верные логин/пароль, When «Войти», Then открывается главная своей роли (клиент → S-02, эксперт → B-01, админ → B-05).
- ⛔ Given неверный пароль, When «Войти», Then «Неверный логин или пароль» без уточнения, что именно неверно; после 5 попыток за 5 мин — пауза 1 мин.
- ⛔ Given клиент вошёл, When он открывает URL back-office, Then экран «Нет доступа», API `403`.

### US-C-02. Профиль компании и выбор компании
Как пользователь, который работает с несколькими компаниями, я хочу выбрать компанию и видеть её профиль, чтобы подавать заявку от правильного юрлица и не вводить данные повторно.
Пр.: Must · Связь: JTBD-2, P-C3, P-C8 · Экран: S-02 (переключатель), S-05 шаг 1 · Тест: E2E-05
- Given у пользователя > 1 компании (sidorov), When он на главной, Then в шапке переключатель компаний; заявки и лента — по выбранной.
- Given у компании есть прошлая заявка, When создаётся новая, Then реквизиты и финансы предзаполнены из последнего снимка с пометкой «из прошлой заявки».
- Given в профиле указана роль пользователя в компании (owner/ceo/accountant/authorized), When заявка отправлена, Then в заявке и карточке эксперта видно «Подал: Счётова М. И., главный бухгалтер».
- ⛔ Given пользователь не участник компании, When он запрашивает её данные по API, Then `403`.

### US-C-03. Мастер потребности
Как собственник без банковской экспертизы, я хочу ответить на 2 вопроса о задаче, чтобы увидеть подходящие продукты и понять, почему они подходят.
Пр.: Must · Связь: JTBD-1, P-C1 · Экран: S-03 · Тест: E2E-01 шаг 2, E2E-05
- Given цель «Пополнить оборотные средства», 4 млн ₽, 12 мес., When «Подобрать», Then первым показан «Экспресс-оборотка» с фразой «почему подходит», вторым — «Кредитная линия».
- Given цель «Купить оборудование», When «Подобрать», Then показан только «Инвест-кредит» и пометка «понадобится договор на покупку».
- Given сумма вне лимитов всех продуктов цели, When «Подобрать», Then продукт показан с ближайшей допустимой суммой и подсказкой «максимум для этого продукта — 5 млн ₽».
- ⛔ Given сумма не введена или ≤ 0, When «Подобрать», Then ошибка у поля, запрос не отправляется.

### US-C-04. Автозаполнение анкеты по ИНН
Как собственник бизнеса, я хочу ввести только ИНН, чтобы данные о компании подставились сами.
Пр.: Must · Связь: JTBD-2, P-C3 · Экран: S-05 шаг 1 · Тест: E2E-01 шаг 4, NEG-01, NEG-03
- Given ИНН валиден и есть в моке реестра, When ввод завершён, Then «Наименование», «ОГРН», «Адрес», «ОКВЭД», «Дата регистрации», «Руководитель» заполняются ≤ 2 с и помечены «из реестра».
- Given поле «из реестра» отредактировано, When пользователь уходит с поля, Then метка меняется на «изменено вами» и показывается подсказка «расхождение с реестром может замедлить решение».
- ⛔ Given ИНН не проходит контрольную сумму, When ввод завершён, Then «Проверьте ИНН — в номере ошибка», шаг не отправляется, API `422` с `field = inn`.
- ⛔ Given ИНН отсутствует в моке, When ввод завершён, Then поля остаются ручными, подсказка «Не нашли компанию в реестре — заполните вручную, специалист проверит данные»; заявка не блокируется (далее T10).
- ⛔ Given компания «ликвидирована» в моке (C5), When ИНН введён, Then «По данным реестра компания ликвидирована — подать заявку нельзя», кнопка «Далее» неактивна.

### US-C-05. Карточка продукта и калькулятор
Как клиент, я хочу подвигать сумму и срок и сразу увидеть платёж и переплату, чтобы понять, потяну ли кредит.
Пр.: Must · Связь: JTBD-1, P-C1, P-C7 · Экран: S-04 · Тест: E2E-01 шаг 3, NEG-02
- Given «Экспресс-оборотка», 4 000 000 ₽, 12 мес., When значения выбраны, Then показано «Ставка от 22%», «Платёж от 374 378 ₽/мес.», «Переплата от 492 530 ₽» и пояснение «точные условия — после оценки».
- Given карточка открыта, When пользователь смотрит блок «Что понадобится», Then виден чек-лист документов продукта из `products.yaml`.
- ⛔ Given сумма вне 300 000–5 000 000 ₽ или срок вне 3–24 мес., When значение введено вручную, Then ошибка у поля, кнопка «Оформить» неактивна, API `/calculate` → `422`.

### US-C-06. Многошаговая анкета с автосохранением
Как бухгалтер, которого отвлекают, я хочу выйти из анкеты и вернуться к тому же шагу, чтобы не заполнять заново.
Пр.: Must · Связь: JTBD-2, P-C6 · Экран: S-05 · Тест: E2E-08
- Given изменено поле в черновике, When прошло 1 с без ввода или пользователь перешёл на другой шаг, Then `PATCH /applications/{id}` сохраняет данные, у шапки «Сохранено в 14:32».
- Given черновик сохранён, When пользователь входит снова, Then на главной ACTION-карточка «Заявка не отправлена» ведёт на последний открытый шаг с данными.
- Given у поля есть термин («Долговая нагрузка», «ОКВЭД»), When наведение/фокус на «?», Then тултип с объяснением простыми словами.
- ⛔ Given сеть недоступна, When автосохранение не удалось, Then баннер «Не удалось сохранить — повторим автоматически», данные остаются в форме; повтор каждые 5 с.
- ⛔ Given заявка уже не DRAFT, When приходит `PATCH`, Then `409 INVALID_TRANSITION`.

### US-C-07. Документы по чек-листу
Как клиент, я хочу видеть, какие документы нужны именно для моего продукта, и загрузить их в кабинет, чтобы банк не запрашивал их потом.
Пр.: Must · Связь: P-C5, P-B1 · Экран: S-05 шаг 4, S-07 · Тест: E2E-01 шаги 4, 6, NEG-07
- Given продукт «Экспресс-оборотка», When открыт шаг «Документы», Then чек-лист: «Налоговая декларация за последний год» со статусом «не загружен».
- Given загружен PDF ≤ 10 МБ, When загрузка завершена, Then статус «загружен», имя и размер файла, кнопка «Удалить».
- Given обязательный документ не загружен, When пользователь жмёт «Далее», Then предупреждение «Без декларации банк запросит её позже — это может задержать решение» и выбор «Загрузить сейчас» / «Продолжить без документа».
- ⛔ Given файл `.exe` или > 10 МБ, When выбран, Then ошибка у пункта, API `415` / `413`, другие данные заявки не затронуты.

### US-C-08. Отправка заявки и живой таймлайн
Как клиент, я хочу после отправки видеть, на каком этапе заявка и что дальше, без перезагрузки страницы.
Пр.: Must · Связь: JTBD-3, P-C2, P-B3 · Экран: S-05 шаг 5, S-06 · Тест: E2E-01 шаги 5–6, NEG-04
- Given все шаги валидны и согласия отмечены, When «Отправить», Then `202`, переход на S-06, статус «Заявка принята», шаг 1 таймлайна отмечен временем.
- Given заявка в автоматическом конвейере, When меняется статус, Then таймлайн обновляется ≤ 5 с без перезагрузки (SSE, фолбэк polling 3 с), у шага — заголовок и пояснение из state_machine §2.
- Given статус SCORING/MANUAL_REVIEW, When открыт S-06, Then блок «Что дальше» показывает ожидаемое время по SLA продукта («обычно до 4 часов»).
- ⛔ Given двойной клик «Отправить», When два запроса с одним `Idempotency-Key`, Then создаётся один переход T1, второй ответ идентичен первому.
- ⛔ Given у компании есть активная заявка на тот же продукт, When «Отправить», Then `409 DUPLICATE`, сообщение «У компании уже есть заявка №… на этот продукт» со ссылкой; черновик остаётся DRAFT.
- ⛔ Given согласие на запрос в БКИ не отмечено, When «Отправить», Then кнопка неактивна, API `422`.

### US-C-09. Ответ на запрос информации
Как клиент, я хочу получить точный перечень того, чего не хватает, и ответить в кабинете, чтобы не начинать заявку заново.
Пр.: Must · Связь: JTBD-4, P-C5, P-B1 · Экран: S-07 · Тест: E2E-01 шаги 5–6, E2E-04
- Given статус NEEDS_INFO, When клиент открывает заявку, Then жёлтая плашка «Банку нужны уточнения», список пунктов (тип FILE или FIELD) с комментарием, срок ответа «до 07.11.2026».
- Given все пункты закрыты, When «Отправить ответ», Then T6 → статус «Проверяем данные», ACTION-карточка в ленте исчезает.
- Given запрос от эксперта с пунктом FIELD «Подтвердите адрес», When клиент выбирает «Адрес из реестра верный», Then поле анкеты обновляется до значения реестра, в истории — «Адрес исправлен клиентом».
- ⛔ Given закрыты не все пункты, When клиент на экране, Then кнопка «Отправить ответ» неактивна с подсказкой «Осталось: 1 пункт»; API `422`.
- ⛔ Given истёк срок ответа, When клиент открывает заявку, Then статус «Срок истёк», загрузка недоступна, CTA «Подать новую заявку».

### US-C-10. Результат: одобрение или контроффер
Как клиент, я хочу понять предложенные условия и чем они отличаются от запрошенных, чтобы принять осознанное решение.
Пр.: Must · Связь: JTBD-5, P-C4, P-C7 · Экран: S-08 · Тест: E2E-01 шаг 7, E2E-03, E2E-05, NEG-12
- Given APPROVED, When открыт S-08, Then сумма, срок, ставка, ежемесячный платёж, переплата, «предложение действует до {дата}», кнопки «Принять и подписать» / «Отказаться».
- Given APPROVED_WITH_CHANGES (C1), When открыт S-08, Then таблица «Вы просили 4 000 000 ₽ / Мы предлагаем 3 000 000 ₽», изменённые строки подсвечены, фраза «По результатам оценки мы можем сразу одобрить до 3 000 000 ₽», топ-3 фактора без баллов.
- Given `changeType = PRODUCT` (C7), When открыт S-08, Then заголовок «Вам больше подойдёт кредитная линия», карточка линии и объяснение разницы в платеже.
- Given «Отказаться», When подтверждение, Then T19 → «Заявка отменена», причина (опц.) сохраняется.
- ⛔ Given оффер истёк, When «Принять», Then `409 OFFER_EXPIRED`, статус «Срок истёк», кнопки неактивны.
- ⛔ Given любой исход, When клиент смотрит объяснение, Then в тексте нет баллов, кодов (`SF-02`, `DEBT_LOAD`) и названий классов риска.

### US-C-11. Отказ с причинами и альтернативой
Как клиент, получивший отказ, я хочу понять причины и что можно сделать, чтобы не чувствовать себя обвинённым и знать следующий шаг.
Пр.: Must · Связь: JTBD-5, P-C4 · Экран: S-08 · Тест: E2E-02
- Given REJECTED (C2), When открыт S-08, Then заголовок «Сейчас не можем одобрить», 3 причины простыми словами (просрочки, нагрузка, падение выручки), блок «Что можно сделать», «Повторно подать можно через 3 месяца».
- Given REJECTED и класс не D, When открыт S-08, Then CTA «Подобрать другой вариант» ведёт в мастер с предзаполненной целью.
- ⛔ Given REJECTED, When клиент пытается вызвать `offer/accept`, Then `409 INVALID_TRANSITION`.

### US-C-12. Подписание (имитация)
Как клиент, принявший оффер, я хочу подписать договор в кабинете, чтобы получить деньги без визита и SMS.
Пр.: Must · Связь: R-21, R-22 · Экран: S-09 · Тест: E2E-01 шаг 8, NEG-11
- Given статус SIGNING, When открыт S-09, Then договор-заглушка с параметрами оффера, чекбокс «Ознакомлен с условиями», код из 6 цифр на экране, пометка «Демо-режим: подпись юридической силы не имеет».
- Given чекбокс отмечен и введён верный код, When «Подписать», Then T21 → DISBURSED, переход на S-10.
- ⛔ Given неверный код, When «Подписать», Then «Код не совпадает, осталось попыток: 2»; после 3 ошибок генерируется новый код; статус остаётся SIGNING; API `422 SIGN_CODE_INVALID`.
- ⛔ Given чекбокс не отмечен, When экран открыт, Then кнопка «Подписать» неактивна.

### US-C-13. Кредит выдан и график
Как клиент, я хочу увидеть, что деньги зачислены, и график платежей, чтобы спланировать бюджет.
Пр.: Must · Связь: JTBD-3 · Экран: S-10 · Тест: E2E-01 шаг 9
- Given DISBURSED, When открыт S-10, Then «Кредит выдан», сумма «зачислено на счёт (демо)», дата и сумма ближайшего платежа, таблица графика (дата, платёж, основной долг, проценты, остаток).
- Given график аннуитетный, When сумма платежей сложена, Then она равна сумма + переплата из оффера (± 1 ₽ округления).
- ⛔ Given статус не DISBURSED, When запрашивается `GET /loans/{id}`, Then `404`.

### US-C-14. In-app уведомления
Как клиент, я хочу видеть уведомления о событиях заявки в кабинете, чтобы ничего не пропустить без email и SMS.
Пр.: Must · Связь: JTBD-3, R-21 · Экран: S-11, колокольчик в шапке · Тест: E2E-01, AC-11
- Given произошёл переход заявки, When клиент в кабинете, Then счётчик колокольчика увеличивается ≤ 5 с, в S-11 — запись со ссылкой на заявку.
- Given уведомление открыто, When клиент вернулся в список, Then оно отмечено прочитанным.
- ⛔ Given любое событие, When система формирует уведомление, Then канал только in-app; в коде и конфиге нет отправки email/SMS.

### US-C-15. Персональная новостная лента
Как клиент, я хочу видеть на главной подсказки и новости, которые относятся к моей отрасли и стадии заявки, чтобы понимать, что делать дальше.
Пр.: Must · Связь: R-07, P-C1, P-C2, P-C4 · Экран: S-02 · Тест: E2E-06
- Given anna без заявок, When открыта главная, Then сверху «Как выбрать кредит под задачу», OFFER «Экспресс-оборотка», INDUSTRY про общепит.
- Given заявка anna перешла в NEEDS_INFO, When открыта главная, Then первой закреплена ACTION «Банку нужны уточнения по заявке №…».
- Given карточка на экране, When «Почему я это вижу?», Then показан `reason` («Ваша заявка сейчас на этапе оценки»).
- ⛔ Given igor с классом риска D, When открыта главная, Then OFFER-карточек нет.

### US-C-18. Отзыв заявки
Как клиент, я хочу отозвать заявку, если передумал, чтобы она не висела у банка.
Пр.: Must · Связь: P-B6 · Экран: S-06 · Тест: E2E-07
- Given статус DRAFT, NEEDS_INFO или MANUAL_REVIEW, When «Отозвать» и подтверждение, Then T22 → «Заявка отменена», заявка исчезает из очереди эксперта.
- ⛔ Given статус SCORING (автоматический), When клиент смотрит S-06, Then кнопки «Отозвать» нет; API `409 INVALID_TRANSITION`.

### US-C-16. Сравнение продуктов (Should)
Как клиент, я хочу сравнить 2–3 продукта в таблице (ставка, срок, платёж, залог), чтобы выбрать.
- Given в мастере ≥ 2 рекомендации, When «Сравнить», Then таблица с одинаковыми строками и рассчитанным платежом для введённых суммы и срока.

### US-C-17. Предварительная оценка шансов (Should)
Как клиент, боящийся отказа, я хочу до отправки увидеть ориентир шансов, чтобы скорректировать сумму.
- Given заполнены шаги «Компания» и «Финансы», When открыт шаг «Параметры», Then индикатор «Высокие / Средние / Низкие шансы» по нагрузке и истории из моков и подсказка «Снизьте сумму до … для высоких шансов». Индикатор не является решением — текст «Это не решение банка».

### US-C-20. ИИ-объяснение (Could) · US-C-21. OCR реквизитов (Could) · US-C-22. Скачать договор (Should)
- US-C-20: Given `LLM_ENABLED=true`, When открыт S-08, Then под шаблонным объяснением блок «Простыми словами» от open-weights модели; Given модель недоступна — блок скрыт, шаблон остаётся (NEG-08).
- US-C-21: Given загружен PDF декларации, When распознавание успешно, Then выручка предложена для подстановки с подтверждением пользователя.
- US-C-22: Given SIGNING или DISBURSED, When «Скачать договор», Then PDF-заглушка с параметрами оффера и водяным знаком «ДЕМО».

## Back-office

### US-B-01. Очередь заявок
Как кредитный эксперт, я хочу видеть заявки, ожидающие решения, с фильтрами и SLA, чтобы начинать с самых срочных.
Пр.: Must · Связь: JTBD-6, P-B2, P-B6 · Экран: B-01 · Тест: E2E-03, E2E-07
- Given вход эксперта, When открыта очередь, Then по умолчанию фильтр MANUAL_REVIEW; колонки: номер, компания, ИНН, продукт, сумма, статус, класс, причина маршрута, время в статусе, индикатор SLA (зелёный < 50%, жёлтый 50–100%, красный > 100%).
- Given фильтры по статусу/продукту/классу или поиск по ИНН, When применены, Then список обновляется; счётчики по статусам в шапке.
- ⛔ Given заявка отозвана клиентом (CANCELLED), When очередь обновляется, Then заявки в фильтре MANUAL_REVIEW нет ≤ 5 с.
- ⛔ Given роль CLIENT, When `GET /backoffice/applications`, Then `403`.

### US-B-02. Карточка заявки эксперта
Как эксперт, я хочу видеть все данные заявки в одном месте, чтобы принять решение без переключения систем.
Пр.: Must · Связь: JTBD-6, P-B4, P-B7 · Экран: B-02 · Тест: E2E-03, E2E-04, NEG-09
- Given заявка C3, When открыта карточка, Then вкладки: Анкета · Данные реестров `[MOCK]` · Кредитная история `[MOCK]` · Скоринг (655, класс A, факторы с баллами, версия правил `2026.10-v1`) · Документы · История событий; справа панель решения.
- Given анкета расходится с реестром (C4 адрес), When открыта вкладка «Данные реестров», Then поле подсвечено, рядом оба значения.
- Given заявка проходила скоринг дважды (C4), When открыта вкладка «Скоринг», Then история «465 → 490» и какие факторы изменились.
- ⛔ Given БКИ не ответил (C6), When открыта карточка, Then баннер «Неполные данные: кредитная история не получена после 3 попыток», вкладка скоринга — «Скоринг не рассчитан», решение всё равно доступно.

### US-B-03. Одобрить / одобрить с изменениями
Как эксперт, я хочу одобрить заявку как есть или с другими суммой, сроком, ставкой, чтобы выдать кредит на приемлемых условиях.
Пр.: Must · Связь: JTBD-6, R-24 · Экран: B-03 · Тест: E2E-03, E2E-04
- Given MANUAL_REVIEW, When открыта панель, Then поля предзаполнены рекомендованным оффером системы (C3: 12 000 000 ₽ / 48 мес. / 19%).
- Given эксперт изменил сумму/срок/ставку и ввёл комментарий, When «Одобрить с изменениями» и подтверждение, Then T16b, клиент видит «Есть предложение» ≤ 5 с, в истории автор и комментарий.
- ⛔ Given «с изменениями» без комментария, When отправка, Then кнопка неактивна, API `422`.
- ⛔ Given сумма вне лимитов продукта, When отправка, Then `422` с полем `amount`.
- ⛔ Given заявка уже решена другим экспертом / отозвана, When отправка со старой `version`, Then `409 VERSION_CONFLICT` / `INVALID_TRANSITION`, панель предлагает обновить карточку.

### US-B-04. Отказать с причиной
Как эксперт, я хочу отказать с причиной из справочника, чтобы клиент получил понятное объяснение, а решение было проверяемым.
Пр.: Must · Связь: JTBD-7, P-B5 · Экран: B-03 · Тест: NEG-10
- Given MANUAL_REVIEW, When выбрана причина из справочника (`HIGH_DEBT_LOAD`, `NEGATIVE_HISTORY`, `UNVERIFIED_DATA`, `COLLATERAL_INSUFFICIENT`, `OTHER`) и введён комментарий, Then T16c, клиент видит клиентский текст причины, не комментарий эксперта.
- ⛔ Given причина или комментарий не заполнены, When «Отказать», Then кнопка неактивна, API `422`.

### US-B-05. Запросить информацию
Как эксперт, я хочу запросить у клиента конкретные документы или уточнения, чтобы не отказывать из-за недостатка данных.
Пр.: Must · Связь: JTBD-4, P-B1 · Экран: B-03 · Тест: E2E-04
- Given MANUAL_REVIEW, When выбраны пункты чек-листа (документ из справочника или поле анкеты) и введён комментарий, Then T17 → NEEDS_INFO, клиент видит перечень и комментарий.
- Given клиент ответил, When заявка снова дошла до MANUAL_REVIEW, Then эксперт видит ответ, новый скоринг и историю.
- ⛔ Given перечень пуст, When «Запросить», Then кнопка неактивна, API `422`.

### US-B-08. Журнал аудита
Как администратор, я хочу видеть все переходы заявок с автором и временем, чтобы проверить корректность процесса.

- ⛔ Given любой пользователь, When пытается изменить или удалить запись журнала через API, Then эндпоинта нет (`405`), журнал append-only.

### US-B-09. Сброс демо-данных
Как администратор демо-стенда, я хочу одним действием вернуть данные в исходное состояние, чтобы каждый показ был детерминированным.

- ⛔ Given `DEMO_MODE=false`, When `POST /admin/demo/reset`, Then `404`.

## Система

### US-S-01. Обогащение данными внешних источников
Как банк, я хочу автоматически получать данные реестров и кредитной истории по заявке, чтобы эксперт и скоринг работали с проверенными данными.
Пр.: Must · Связь: P-B4, P-B7, R-20 · Тест: E2E-01, NEG-09
- Given статус ENRICHING, When моки ответили OK, Then EnrichmentResult по каждому источнику сохранён, T8 → SCORING.
- ⛔ Given БКИ отвечает `504` (C6), When 3 попытки с паузой 1/2/4 с исчерпаны, Then T10 → MANUAL_REVIEW с флагом `incompleteData`, сервис не падает.
- ⛔ Given реестр вернул статус LIQUIDATED, When обогащение, Then T9 → REJECTED, `REGISTRY_STOP`.

### US-S-02. Скоринг и авто-решение
Как банк, я хочу, чтобы простые заявки решались автоматически по прозрачным правилам, а серая зона уходила эксперту.
Пр.: Must · Связь: JTBD-6, P-B2, R-24 · Тест: E2E-01, E2E-02, E2E-05, автотест `expected_outcomes`
- Given seed-компании C1…C7, When заявки проходят конвейер, Then баллы, классы и исходы совпадают с таблицей [scoring_and_decision §7](../process/scoring_and_decision.md) (выход `tools/reference/expected_outcomes.py --json`).
- Given `DEMO_STEP_DELAY_MS=3000`, When конвейер работает, Then между автоматическими переходами пауза 3 с ± 0,5 с.
- ⛔ Given ScoringResult сохранён, When клиент запрашивает `GET /applications/{id}`, Then в ответе нет `score`, `riskClass`, `points`, `reasonCodes` — только `clientText`.

### US-S-03. Таймеры истечения
Как банк, я хочу закрывать заявки, по которым клиент не ответил, чтобы очередь и отчётность не засорялись.
Пр.: Must · Связь: P-B6 · Тест: NEG-12
- Given NEEDS_INFO дольше `INFO_REQUEST_TTL_MINUTES`, When сработал планировщик, Then T7 → EXPIRED, уведомление клиенту.
- Given оффер с `expiresAt` в прошлом, When планировщик, Then T20/T23 → EXPIRED.
- ⛔ Given клиент ответил за секунду до таймера, When гонка, Then побеждает первая транзакция по `version`, вторая получает `409`, заявка не оказывается в двух статусах.
